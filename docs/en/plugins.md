# Unified packages and feature plugins

> **Purpose:** Build and review Lua feature plugins in unified `.ntpkg` packages, including their API, limits, and security model.
>
> **On this page:** [Lua API](#lua-api-2) · [Data and logging](#declared-data) · [Security and lifecycle](#security-and-lifecycle) · [Debugging](#debugging)


A package's identity comes from `package.toml` and its styling from `skin.toml`. `capabilities` can combine `skin`, `resources`, `lua` and `sounds` ([sound packs](skins.md#sound-packs)).

Built-in skins and user packages share the same format and validation rules.

Built-in resources are generated by the build tooling from a directory scan, and their manifests are pre-parsed into cacheable data at build time; the runtime still applies the same format and rules, and a development directory is re-read on every reload.

A skin ID is used only for selection, indexing and dependency resolution — it never drives rendering decisions.

The format version is `format = 1`, `schema = 3`.

Packages are stored together in `packages/` under the app data directory.

The Steam edition also reads subscribed Workshop items; these are read-only external package directories and are not copied into `packages/` ([Steam edition](steam.md)).

Older formats are not supported, and the old `skins/` directory is neither migrated nor deleted.

Dependencies are listed in `[dependencies]` by package ID with an exact three-part version; resource references are either paths relative to the package or `pkg:<package ID>/<path>`.

Common fonts can be referenced via `builtin:fonts/...`.

Missing, conflicting or circular dependencies and out-of-bounds resources cause the package to be rejected.

Export places dependencies in `dependencies/<package ID>/` by default, together with their asset licenses.

## Lua API 2

A feature package additionally declares `capabilities = ["lua"]` and a `[lua]` table: `entry` is the UTF-8 source entry point, and `reads` lists the declared data the script may read (empty by default). Scripts receive only value-type events and return declarative views; they never touch the app's internal objects or Rust message enums.

```toml
[lua]
entry = "main.lua"
reads = ["phrases"]          # this package's data; a dependency's data is "pkg:<package ID>/<data ID>"

[data.phrases]
path = "data/phrases.json"
format = "json"              # text, json, nthz; parsed by declaration, not by extension
format_version = 1
source = "作者自制"
license = "MIT"
constraints = { type = "object", required = ["phrases"], max_depth = 3 }
```

```lua
local count = 0
return {
    on_event = function(event)
        if event.type == 'line_start' then count = count + 1 end
    end,
    view = function()
        return {views = {{slot = 'panel', root = {
            kind = 'text', id = 'counter', text = tostring(count)
        }}}}
    end,
}
```

- Events include `init` (`reads` lists the readable data), `data`, `command`, line playback start/end `line_start`/`line_end`, `speaking`, `expression`, `portrait`, `shake`, `vts` and `chat_message` (platform `blivechat`/`laplace`/`comet`/`twitch`, author, plain text). Event fields are local values the host has already produced; they never contain account credentials.
- `commands = {{id = 'reset', label = 'Reset'}}` declares local commands. The host shows an entry for each command and, when it is activated, sends `{type='command', id='reset'}` back to the originating plugin; commands cannot invoke arbitrary app actions.
- View slots are `display`, `history`, `input` and `panel`, corresponding to the display, history, input content area and the plugin panel. Generic UI still uses its own neutral theme.
- Components are `column`, `row`, `text`, `button` and `canvas`; every component needs a stable, unique `id`. Lua functions can compose and return these nodes to define reusable components.
- Containers use `children`. `text` is literal text — no rich text, links or HTML; `button` reports back through `command` and supports the keyboard and accessibility behaviour of the host's buttons.
- `canvas` declares `width`, `height` and `draw`. Drawing supports `rect` (`rect=[x,y,w,h]`, RGBA `color`, `radius`) and `path` (`points`, `color`, `closed`, `width`). The host draws and caches the result, so Lua never runs in the per-frame drawing path. Advanced skin effects are still expressed through the restricted WGSL interface.

### Declared data

`nana.data.request(id, query)` may only request data listed in `reads` and returns a token immediately; the host later delivers the results in a `{type='data', results={{token=…, value=…} or {token=…, error=…}}}` event, so the first `view()` has no data yet. Queries are `{kind='info'}`, `{kind='whole'}`, text `{kind='lines', start, count}`, JSON `{kind='pointer', pointer='/a/0'}` and `{kind='slice', pointer, start, count}`, and stroke-order data `{kind='glyph', char='心'}`. Results are plain values — no paths, handles or host objects; JSON `null` becomes `nil` in Lua.

The host answers from the content snapshot taken when the user consented to enable the plugin, which was fully validated against its declared format at import.

Each dispatch allows at most 8 requests, each host event at most 4 rounds of chained requests, 64 KiB per result and 120 KiB per round in total (error replies included), and at most 1024 lines per `lines`/`slice` request.

Exceeding a budget returns an error rather than truncating, so large data must be queried in chunks.

Requests still unanswered when the next host event arrives are discarded.

See [Unified package design](../package-design.md) for the full description of data formats, constraints and budgets.

### Logging

`nana.log(level, message)` writes a line to NanaType's session log. `level` is `'debug'`, `'info'`, `'warn'` or `'error'`; any other value is a script error. `message` is converted with `tostring`, must be UTF-8, and is truncated at a character boundary beyond 512 bytes. Each dispatch keeps at most 16 lines and only counts the rest; the host further limits each plugin to 10 lines per second, and the number of dropped lines is written with the next record. `debug` and `info` are recorded only when the user turns on "Detailed logs"; `warn` and `error` are always recorded.

Lines are written as `[plugin ID] message` and redacted just like the app's own logs: query strings are stripped from URLs, values such as cookies and tokens become `***`, and the home directory becomes `~`.

Diagnostic bundles exported by users include these lines, so never log chat content, accounts or other personal information.

NanaType Editor's debugger shows all levels.

See [Logging](logging.md) for the overall design.

A complete installable example lives in `docs/examples/counter-plugin/`; the packaged [counter-plugin.ntpkg](../examples/counter-plugin.ntpkg) can be imported and enabled under "Plugins & packages".

It counts the lines that have played and provides a canvas progress bar and a reset button. `docs/examples/phrase-plugin/` ([phrase-plugin.ntpkg](../examples/phrase-plugin.ntpkg)) shows how to declare JSON data and query it value by value, one line at a time.

After editing the sources, regenerate the archives with `python scripts/assets/package-example-plugins.py`.

## Security and lifecycle

"Review source and request activation" in Settings shows, one by one, the author, creation date, license, licensee, script entry, readable data (owning package, format version, size, source, license and whether it is signature-protected), package location, signature status and content fingerprint.

The user must actively tick the box confirming the source is trustworthy and that they understand the risks, then click "Consent and start this plugin".

No code runs before confirmation.

Enabled IDs from old settings do not create new trust records.

Consent records carry a policy version — policy 2 added declared data reads, so earlier consents must be reviewed again.

Consent is bound to the full content of the package and its dependencies, so any update requires confirming again.

Disabling also revokes consent; a reload can only reuse a consent that still matches the current content.

If the package or dependency directory of a running plugin changes on disk, the host recomputes the content fingerprint in the background and, if it no longer matches the one at startup, terminates the plugin and asks for confirmation again.

The `author`, `created_at` (optional, `YYYY-MM-DD`), `licensed_to` and `license` fields in `package.toml` apply equally to every capability. The licensee is a person, organization or "all users" as declared by the author; it is not bound to any account. Missing information is shown as "Not provided"; the author's identity or the creation date is never inferred.

The optional `package.integrity.json` uses an Ed25519 signature covering the protection policy, the package's file list and BLAKE3 digests of the protected files. `package.toml` must be protected.

Files marked editable may be modified; any change to other protected content or to the signing policy causes the package to be rejected.

Dependencies verify their own signatures independently, and their full content is additionally covered by the consent fingerprint.

Exporting a signed package keeps the original signature bytes.

Source code is always readable; the UI clearly distinguishes unsigned, failed verification and verified signatures, and shows whether the script entry is within the protected set.

A valid signature only means the content matches that public key — it does not authenticate the author.

Files allowed to be edited are not guaranteed to still be the author's original work.

Stripping a signature does not keep a "valid signature" state, and the content fingerprint changes too, invalidating any earlier consent.

This mechanism is neither encryption nor unbreakable DRM.

Authors choose which files to protect and sign them in the [package editor](package-editor.md) (the standalone NanaType Editor); the private key is kept only in the system's protected storage.

The official app ships a fixed Lua interpreter compiled to Wasm; authors distribute only UTF-8 Lua source. Each enabled plugin runs in its own worker process; importing or referencing resources never runs a script automatically. Disabling terminates the worker process and unmounts its views, and reloading creates a fresh instance; Lua memory state is not persisted.

The interpreter is not connected to any WASI or OS implementation.

All file, process and similar imports in the compiled artifact are bound to refuse; the environment interface returns only an empty environment and never passes through the host's.

Plugins have no API for network, files, external programs, clipboard, accounts, persistent storage or system access. `io`, `os`, `package`, `debug`, `require`, `load`, `loadfile`, `dofile` and `string.dump` are all unavailable; scripts cannot load native modules or bytecode, or replace the interpreter.

The host UI protocol does not accept URLs, paths or arbitrary message dispatch.

Default limits: 128 KiB of source, 256 KiB per IPC message, 32 MiB of Wasm linear memory, 20 million fuel plus an interrupt budget of about 50 ms per execution of plugin code, 512 components, 32 levels of component nesting, 2048 draw commands, 256 points per path, 8192 geometry points in total, 16 KiB of component text in total, 32 queued events, at most about 30 view updates per second per plugin (about 6 for a canvas at full budget), and at most 8 enabled instances.

The host reads views directly through the Lua C API without running plugin code or metamethods, and checks every item for finite numbers, sizes, text length, ID uniqueness and unknown fields; it never trusts validation done by the child process itself.

See [Plugin performance, budgets and isolation](../plugin-performance.md) for the full budgets and measurements.

Worker startup may take up to 15 seconds, and the normal event response deadline is 200 ms.

Timeouts, crashes and invalid responses terminate the plugin, and the process is reclaimed immediately.

When events back up, the worker processes them back to back and publishes only the latest view; the UI does not replay intermediate states.

The fixed interpreter is precompiled during the Rust build and loaded from the artifact embedded in the app at startup; IPC, package review, signature verification and import/export all run in the background, so the UI thread never waits.

Wasmtime traps and uncaught Lua errors invalidate the instance; after an error the plugin must be reloaded explicitly.

Lua's `pcall` can catch ordinary script errors but cannot bypass the execution limits.

OS isolation: on macOS the worker applies a deny-by-default Seatbelt profile before reading any request; file, network and process creation have been verified as denied on macOS.

On Windows the host places the worker in a job object; starting, stopping and reclaiming worker processes in the release app has been verified, and native tests additionally check the limits in the kernel, verifying that child process creation is denied, the 256 MiB committed memory cap, and termination once the job handle is closed.

UI restrictions such as desktop and clipboard are currently only checked at the configuration level, without running destructive system operations one by one.

AppContainer is not implemented yet, and the job object does not isolate files or network.

See [Plugin performance and isolation](../plugin-performance.md) for the current budgets, measurement methods and verification scope.

## Debugging

The [package editor](package-editor.md) can debug draft scripts in the same kind of isolated worker process used by real plugins.

Debugging requires a separate confirmation that you trust the current content, and any edit stops the instance and revokes that confirmation.

Test events are sent manually by the user, and returned views appear only in the debug panel.

Debug confirmation is not activation consent: after exporting and importing, the plugin must still be reviewed and enabled under "Plugins & packages".

## Verification

`cargo test -p nanatype-plugins` covers normal events, unavailable system interfaces, malicious input, infinite loops and memory exhaustion; `cargo test -p nanatype-theme` covers the package format, dependencies, inheritance, import/export and skin configuration. All skins must still pass the display/history/input screenshots and the default and 300px narrow-window layout checks.

The interpreter's origin, checksums and license are in `crates/plugins/runtime/README.md`. Running plugins does not require users to install Lua, Node.js or Wasmtime.
