# OBS / Spout 出力

Windows では、表示ウィンドウ、パートナーの表示ウィンドウ、履歴をそれぞれ Spout2 で GPU 共有テクスチャとして送信でき、OBS では Spout2 プラグインの *Spout2 Capture* で受信します。使い方は[使い方ガイド](usage.md)の OBS の節を参照してください。このページでは送信側のライフサイクルと実測結果を説明します。

## 送信側のライフサイクル

- **フレームの受け渡し**：NanaUI の DX12 レンダリング結果を D3D11 ブリッジデバイス経由で Spout の共有サーフェスにコピーし、1 つの共有フェンスで受け渡します。前回の release が完了するまで次の ready は発行しません。同じデバイス世代・同じアダプター上のすべての出力は 1 つの D3D11 デバイスと immediate context を共有し、各 sender は登録・共有サーフェス・インポートしたテクスチャ・フェンスを個別に持つため、1 つの出力を破棄しても他には影響しません。
- **動的なピクセル**：WGSL エフェクトと光沢スイープは、ピクセルが時間とともに変化することを宣言します（NanaUI `SceneGpuRenderer::content_version`）。そのため本文が静止していても、ネイティブで保持された出力が古い画面を再利用することはありません。
- **すばやい再オープン（5 秒）**：出力をオフにするとまず透明なフレームを送って一時停止し、sender を最大 5 秒間保持します。同じ名前・サイズ・アルファで再度開くと、元の sender、共有テクスチャプール、フェンスを再利用し、現在の本文を再発行します。名前の変更、サイズやアルファの変更、名前の衝突、デバイス世代の変化があれば再利用しません。透明フレームの発行に失敗した場合は sender をすぐに破棄し、古い本文が OBS に固まって残らないようにします。再利用待ちの sender は出力ごとに最大 1 つ、アプリ全体で最大 3 つです。設定の繰り返し変更やホットリロードで期限が延びることはありません。
- **コールド再接続（30 秒）**：5 秒が過ぎると送信元の登録を解除して画像リソースを解放し、画像やフェンスを持たないデバイスだけを残します。最後の出力を閉じてから 30 秒経つとデバイスも解放します。出力を有効にすると、アプリの更新フェーズで sender を作成します。固定サイズがわかっている場合は先に透明なサーフェスを発行し、OBS による検出と最初のフレームのレンダリングを並行させます。
- **SDK の修正**：Spout SDK は sender を作成するたびにすべてのディスプレイモードを列挙します（1 出力あたり約 20 ms）。ビルド時に `OUT_DIR` 内の SDK のコピーで、これを 1 回の `ENUM_CURRENT_SETTINGS` クエリに置き換え、失敗時は 60 Hz にフォールバックします。元の関数が変わった場合はビルドが失敗し、明示的なレビューを求めます。
- 後片付けは既存のタイマースレッドと 1 つのクリーンアップタスクで行い、フレームごとのポーリングはしません。アプリを終了するとすべての sender を解放します。

## 実測結果

2026-10-17、Windows、RTX 5060、DX12、150% DPI。公式のポータブル版 OBS 32.2.2 と OBS Spout2 Plugin 1.12.0、1920×1080 / 60 fps で、Display 960×320 と History 960×360 の 2 系統を実際に受信し、3 つのネイティブウィンドウを同時に動かしました。録画はローカルのテストソースのみで、配信はしていません。

- **負荷テスト**：約 4 分間で 24 種のスキンを 3 周し計 79 回切り替え、ホット保存 20 回（うち 4 回は不正な内容）、ウィンドウの非表示、サイズの交互変更、出力の再起動を実施。5,054 回の送信はすべて成功し、フェンスの pending=0、デバイスロストなし。OBS のレンダリング・エンコードのフレーム落ちはいずれも 0。送信コールバックの CPU 時間は中央値で約 0.13 ms、sender を作り直したときに 1 回だけ最大約 90 ms となり、すべてのフレームで 16.7 ms を下回るとは約束できません。
- **すばやい再オープン**：5 秒以内の再オープン 24 回はすべて元の共有プールを再利用しました。閉じるたびに OBS 上で確実に空白になり、復帰後に空白がちらつくこともありませんでした。
- **コールド再接続**：同じ条件で 6 秒間閉じる操作を 8 回行ったときの、OBS の画面が復帰するまでの中央値（ピクセル精度は約 1 フレーム）：

| 有効化コマンドから OBS の復帰まで | Display | History |
| --- | ---: | ---: |
| 5 秒以内のすばやい再オープン | 28.1 ms | 14.5 ms |
| 6 秒のコールド再接続、最適化前 | 178.9 ms | 119.5 ms |
| 6 秒のコールド再接続、最適化後 | 69.6 ms | 62.3 ms |
| 32 秒の完全なコールドスタート、最適化後 | 93.0 ms | 93.0 ms |

- **リソースの回収**：オン／オフを繰り返しても、ハンドル、スレッド、送信元の登録は回数に応じて増えず、終了後に幽霊の送信元も残りません。閉じた後はエフェクトインスタンスのマスク、パラメーターのバインド、スケールの記録、コンパイルキューがゼロに戻り、上限付きのウォームアップ済みプログラムキャッシュ（約 13.75 MiB）だけが残ります。

OBS プラグインには 100 ms ごとの検出ポーリングがあり、完全に回収した後はデバイスと画像リソースを作り直す必要があるため、空白フレームがゼロであることは保証しません。数時間の配信、アダプターをまたぐ構成、ドライバーの障害注入、その他の GPU ドライバーはまだ検証しておらず、macOS の Syphon も実測していません。

## ゲームと同時に動かす

ゲームやエンコーダーが GPU / CPU を使い切っている場合は、**設定 › 出力 / OBS › パフォーマンス**（Windows のみ）で次の項目をオンにできます。

- **GPU の優先度を上げる**：プロセス全体の GPU スケジューリング優先度を High にし、実行速度のスロットリングをオフにします。システムの制御がひとつでも拒否された場合は全体を Normal に戻し、「**適用されていません**」と表示します。
- **CPU の優先度を上げる**：フレームが待つスレッド（すべてのウィンドウを描画して Spout を送信する UI スレッドと、1 文字ずつのリズムを制御するタイマースレッド）だけを通常より高くします。チャット、ダウンロード、デコードなどのスレッドはシステムのスケジューリングのままです。
- **CPU アフィニティ**：上記のスレッドが P コアを優先して使うようにします（コア番号から推測せず、システムが報告する EfficiencyClass で選びます）。P コアと E コアの区別がない CPU では「**設定は不要です**」と表示されます。

3 つともデフォルトはオフで、設定は `performance` に保存され、再起動後に自動で再適用されます。

同じセクションの「**使用する GPU**」でレンダリングに使うグラフィックカードを選べます（デフォルトは「**自動**」）。Spout でテクスチャを共有する場合、NanaType と OBS が同じカードで動いているとオーバーヘッドが最小になります。GPU デバイスは起動時にしか作成されないため、変更は再起動後に反映されます。起動時に選択した名前を `WGPU_ADAPTER_NAME` に書き込み、選択したカードがもう存在しない場合は自動選択に戻ります。外部で `WGPU_ADAPTER_NAME` がすでに設定されている場合は外部の値が優先されます。カードは名前で照合するため、同じ名前の 2 枚のカードは区別できません。

## デバッグ用サンプル

`cargo build -p nanatype --locked --example native_outputs` で、実際の `Host` に直接処理を委ねるデバッグ用エントリーポイントをビルドできます（Windows の debug / DX12 のみ）。正式な Spout sender を使い、監視スレッドで共有フェンスを観測します。実行前に `NANATYPE_NATIVE_PROBE` を新しい独立したディレクトリに向けてください。通常のインストールディレクトリは読み込まず、この観測機能はリリース版には含まれません。
