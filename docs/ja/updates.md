# アップデートの確認

GitHub 版の更新確認、プロキシ、署名検証、リリース手順を説明します。Steam 版は SteamPipe で更新するため、[Steam 版](steam.md) を参照してください。

**このページの案内**：更新の流れ → プロキシ → 確認とインストール → 署名鍵 → リリース

NanaType は GitHub Release から新しいバージョンを取得します。Steam 版にはこのページで説明するアップデート確認は含まれず（`updates` feature をコンパイルしない）、SteamPipe で更新されます。[Steam 版](steam.md)を参照してください。ファイルはサードパーティのプロキシ経由でダウンロードされることもありますが、信頼できるかどうかは署名とダイジェストだけで判断し、ダウンロード元には左右されません。

## 流れ

1. リリースワークフロー（`.github/workflows/release.yml`、`vX.Y.Z` タグのプッシュで起動）が、Windows のインストーラーとポータブル版、macOS（Apple シリコン）の dmg と zip をパッケージングし、`latest.json`（各ファイルのプラットフォーム、種類、サイズ、SHA-256）とその Ed25519 署名 `latest.json.sig` を生成して、下書きの Release を作成します。
2. クライアント（`crates/update`）は GitHub、内蔵プロキシ、ユーザーが入力したプロキシに対して `releases/latest/download/latest.json` と署名を同時に要求し、内蔵の公開鍵で署名を検証します。最も新しいバージョンの結果を採用し、応答の速さ順にソースを並べます。
3. ダウンロードしながら SHA-256 を計算し、サイズかダイジェストが一致しなければ次のソースに切り替えます。検証に通ったファイルだけをシステムに渡して開きます。

クライアントは `api.github.com` にアクセスしないため、`github.com` のファイルダウンロードをプロキシできるサービスなら何でも使えます。プロキシが返したエラーページ、古いキャッシュ、改ざんされたファイルはすべて拒否されます。複数のソースのバージョン番号を同時に比較するので、プロキシにキャッシュされた古いマニフェストで新しいバージョンが隠れることはありません。

## プロキシ

プレフィックス形式で指定します：`<プロキシ>https://github.com/sena-nana/NanaType/releases/...`。内蔵リストは `crates/update/src/mirror.rs` にあり、2026-10 に実測しました（測定地点は中国本土外）。

| プロキシ | Release ファイル | 備考 |
| --- | --- | --- |
| gh-proxy.com | 利用可。SHA-256 は元ファイルと一致 | Cloudflare バックエンド |
| ghfast.top | 利用可。一致 | |
| ghproxy.net | 利用可。一致 | 100 MB 未満向け |
| gh.llkk.cc、mirror.ghproxy.com | 到達不可 | 未収録 |
| jsDelivr | Release ファイル非対応 | 未収録 |

いずれも個人が運営する無料のサービスで、速度制限やドメインの変更、サービス終了の可能性があるため、転送経路としてのみ使います。**設定 › 一般 › アップデート › カスタムプロキシ** で `https://` で始まるプレフィックスをもう 1 つ追加でき、それが最初に試されます。

## 確認とインストール

「**アップデートを自動確認**」がオンの場合、起動から約 10 秒後にバックグラウンドで確認し、24 時間に 1 回までしか確認しません。新しいバージョンが見つかると通知され、**設定 › 情報** で説明を読んだり、「**このバージョンをスキップ**」や「**ダウンロード**」を選んだりできます。ダウンロードはキャッシュディレクトリの `updates/` に保存され、次回起動時に消去されます。

- Windows のインストール版（プログラムディレクトリに `unins000.exe` がある）：`setup.exe` を実行します。NanaType は先に終了します。
- Windows のポータブル版：zip のあるフォルダーを開くので、ユーザーが展開して置き換えます。
- macOS：dmg を開きます。Intel Mac 向けのビルドはまだありません。

## 署名鍵

```bash
cargo run -p nanatype-update --example keygen
```

`public` は `crates/update/src/sign.rs` の `PUBLIC_KEY` に書き込み、`secret` はリポジトリの Secret `NANATYPE_UPDATE_KEY` として保存し、オフラインでもバックアップしてください。コミットしてはいけません。ワークフローは `--example manifest` でマニフェストを生成して署名し、秘密鍵と公開鍵が一致しない場合は失敗します。

鍵の更新：古いバージョンは古い公開鍵しか信頼しないため、まず古い鍵で署名し新しい公開鍵を内蔵したバージョンをリリースしてから、Secret を差し替えます。秘密鍵が漏れると誰でもマニフェストに署名できてしまうので、すぐに鍵を更新し、GitHub から新しいバージョンを手動でダウンロードするようユーザーに案内してください。

## リリース

1. ルートの `Cargo.toml` の `workspace.package.version` を変更してコミットします。
2. `git tag vX.Y.Z && git push origin vX.Y.Z`（タグはバージョンと一致させること）。
3. 下書きの Release を確認してから公開します。正式に公開されて初めて `releases/latest` がそれを指します。`-` を含むタグはプレリリースとして扱われ、安定版には配信されません。
