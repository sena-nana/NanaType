# Spout 快速重开与有期限回收

2026-10-17。此项继续 [真实 OBS / Spout 验证](obs-spout-validation.md)，专门处理输出开关导致的重连空白。

## 行为与资源寿命

Windows 输出关闭时，不立即注销已有发送器，而是经原有共享纹理与围栏发送一帧透明内容。随后暂停该输出的绘制和发布，最多保留 5 秒。相同名称、尺寸和 alpha 配置的快速重开复用原有 D3D11 sender、原生共享纹理池、围栏及兼容的绘制目标，并重新发布当前正文。

超过期限会释放发送器和输出资源。改名、停用时更改尺寸或 alpha、被另一个启用的输出占用名称、对方离线，以及设备代次变化，都不能复用旧的暂停发送器。透明帧若发布失败则直接撤销发送器，避免把旧正文冻结在 OBS 中。关闭后仍显示为“关闭”，短暂保留的 Spout 注册只承载透明画面。

每个输出最多一个待复用发送器，全应用最多三个；保留期限从首次关闭开始，重复设置或热重载不能延长它。沿用现有计时线程，至多一个输出清理任务，不增加逐帧清理或每次开关新建的线程。恢复会取消旧期限，过期消息只按当前状态检查，不能提前删除后来恢复的发送器。应用退出直接释放全部发送器。

NanaUI 的 `WindowOutputConfig::with_suspended(true)` 保留目标并清空消费方画面，原生窗口继续显示实际场景。暂停时两者不可共享本次栅格化。透明帧完成后，隐藏输出不再持续请求帧；清理在程序更新时同步执行，独立于原生窗口是否可见或是否收到绘制事件。恢复强制更新内容，避免静态历史窗口复用先前的透明像素。

上游实现提交为 [c60068c03](https://github.com/sena-nana/NanaUI/commit/c60068c039590d8938ce784736813e6ce09a2fb2)，并由 [3f521953f](https://github.com/sena-nana/NanaUI/commit/3f521953f0cc4d4d4d853ee93aaf235af56bf5c7) 修正隐藏静态窗口的唤醒期限。应用固定至后者，没有修改 Cargo 缓存或引入本地路径覆盖。

## 验证方法

使用同一台 RTX 5060、DX12、150% DPI、官方便携 OBS 32.2.2 和 Spout 插件 1.12.0。输入、展示框和历史三个原生窗口，Display 960×320、History 960×360 两路真实接收，OBS 1920×1080 / 60 fps。版本来源与下载校验值见前一份报告。只录本地测试源，没有推流。

`scripts/run-obs-spout-reconnect.py` 等待实际 sender 就绪，再执行可见窗口 10 次和全部隐藏 10 次快速开关；中间切换森林、潮汐、华灯和汽水。另在关闭期间保存 WGSL 四次，其中三次有效、一次非法循环，随后进行三轮关闭超过 5 秒的到期回收／冷重连；最终关闭后继续观察 15 秒。

`scripts/analyze-spout-reconnect.py` 逐帧检查 OBS 两路源是否为空，利用录像首尾两个背景色标记对齐命令时钟和视频 PTS。对每次关闭检查已发送透明帧、每次快速重开检查原生共享池代次不变，并测量画面恢复时间。OBS 像素观测精度约一帧（16.7 ms）；原生回调与命令使用同一单调时钟。两者均不是 GPU timestamp 或完整端到端延迟。

`run05` 首次真实测试检出了一个问题：隐藏的静态历史窗口反复得到新的 `Instant::now()` 唤醒期限，调度器不断把期限向后推，透明帧被饿死。该轮不能算关闭语义验收通过。修正后记录固定的事件期限，并增加重复查询期限保持不变的回归断言。

上游 11 项窗口输出测试覆盖透明像素、窗口画面隔离、12 次暂停／恢复后的代次复用、恢复后的静态像素及最终释放。10 项实际 DX12→D3D11 导出测试覆盖共享句柄、围栏和等待消费方 GPU 释放后才关闭资源。应用新增固定期限、取消与合并清理任务、改名／尺寸／alpha／冲突／对方离线测试；165 个应用单元测试通过，2 个原有测试忽略。

## 最终实测

`run06` 使用固定提交 `3f521953f0cc4d4d4d853ee93aaf235af56bf5c7`，解码 4,368 帧 OBS 录像。24 次快速重开中，两路输出全部复用原生共享池，发送器每次均只打开一份池，没有在开关时重复导入共享句柄。

| 从开启命令到恢复 | Display | History |
| --- | ---: | ---: |
| OBS 画面恢复中位数 | 28.1 ms | 14.5 ms |
| OBS 画面恢复 P95 | 48.5 ms | 31.6 ms |
| OBS 画面恢复最大值 | 50.8 ms | 34.1 ms |
| 原生发送回调恢复 P95 | 31 ms | 13 ms |

每路均发送 28 帧暂停透明内容，包含最终关闭；其余暂停时段不继续发送。27 次可配对的关闭／开启中，每次关闭都在 OBS 中确实变为空白，恢复后直到下一次主动关闭没有再检出整区闪空。该轮完整录像新增 OBS 渲染和编码跳帧均为 **0**。首尾标记测得命令／录像偏移 0.12524 和 0.12366 秒，表中像素时间仍应按约一帧精度理解。

本轮共 1,446 次实际发送、1,446 次共享围栏释放，pending=0，SDK failed/skipped/released-without-copy 均为零。release 轮询观测 P95 为 1.60 ms、最大 5.06 ms；这是监测线程观测上界，不能当作 GPU timestamp。

3 轮到期回收后，两路各只创建了 3 个新池，因此全程每路共 4 个代次。每次 1 秒时仍有两个注册源，6 秒检查时均已消失，最终关闭后的检查也没有残留源。应用句柄在快速循环中约 933–945，最终回落至 685；线程从最多约 88 回落至 43。OBS 私有内存从接收时约 541 MiB 回落至约 249 MiB，句柄回落至 2,255。没有随快速开关累计句柄、线程或发送器注册。

应用私有内存经过皮肤预热后约 744–756 MiB，后续冷创建设备后约 818–821 MiB，最终约 797 MiB；不把分配器和驱动未立即归还私有内存解释为资源已泄漏或已全部释放。关闭后的效果实例遮罩、参数绑定、缩放记录及编译队列均为零，保留 11 个有界预热程序，约 13.75 MiB。源码编译总数为 11，包含所选主题和三次有效的新源码；快速开关没有新增逐帧编译。

超时后的 3 次冷重连仍有创建／发现成本：Display 中位约 170 ms、最大约 268 ms；History 中位约 168 ms、最大约 170 ms。短时开关的优化不会以无限期保留资源来掩盖冷创建。详细数值见 [汇总 JSON](spout-reconnect-validation.json)，原始日志、逐次记录与录像在 `obs/run06` 及 `obs/recordings`。

最终应用单元回归再次通过（165 通过、2 个原有忽略）；两仓库格式和 diff 检查、上游 engine boundary 检查通过。构建继续有原有 libvpx 缺少 PDB 的链接警告。

原始记录位于 `E:/NanaType-validation-classic-20261017/obs/`；构建沿用前一份报告的依赖优化参数。复现使用全新隔离目录和 `native_outputs` debug 样例：

```powershell
python scripts/run-obs-spout-reconnect.py <isolated run directory>
python scripts/analyze-spout-reconnect.py <isolated run directory>
```

该优化覆盖短时开关。超时后必须释放资源，再次启用仍走冷创建与 OBS 发现流程。没有跨适配器、驱动故障注入或数小时运行证据，不能将有期限保留解释为无限期无缝重连。


后续对超过 5 秒冷重连的设备复用、SDK 构造与提前注册优化，见 [冷重连验证](spout-cold-reconnect-validation.md)。上文记录的是该次快速重开实现的历史实测。
